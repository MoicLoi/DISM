# 16.14 Platform Integration（平台落盘）

## 目标

让应用**真的**把决策历史存下来，而不是每次启动都从零开始。

```text
16.13 之前：DismFactory.create()        → 内存，关掉就没了
16.14     ：JvmDismFactory.create(file) → SQLite 文件
            AndroidDismFactory.create(ctx) → 应用私有目录
```

## 为什么这不是"接一个 driver"那么简单

动手前先查了现有接口，发现一个**死结**：

```text
DismFactory.create(config)          public，但 provider = null → LOCAL 必然抛错
DismBootstrapper(provider)          @DismInternalApi
DismPersistenceProvider.create()    返回 DismPersistence
DismPersistence                     :core 的 internal 类型   ← 死结
```

`DismPersistenceProvider` 的 KDoc 里写着"Android / JVM / iOS / Server
各自实现它"，还给了 `JvmPersistenceProvider` 的示例——
但那个类**只存在于注释里**，而且按这个签名谁也实现不了：
`DismPersistence` 是 internal，`app` 模块拿不到它。

所以落盘在 16.14 之前是**做不到的**，不是"还没做"。

## 做法

在 `:core` 的**平台源集**里提供公共工厂：

```text
core/src/jvmMain/.../platform/JvmDismFactory.kt
core/src/androidMain/.../platform/AndroidDismFactory.kt
```

```kotlin
@DismPublicApi
object JvmDismFactory {
    fun create(
        databaseFile: File,
        configuration: DismConfiguration = DismConfiguration(),
    ): Dism
}

@DismPublicApi
object AndroidDismFactory {
    fun create(
        context: Context,
        databaseName: String = "dism",
        configuration: DismConfiguration = DismConfiguration(),
    ): Dism
}
```

### 三条设计规则

**1. 公共签名里没有任何内部类型**

只有 `File` / `Context` / `String` / `DismConfiguration` / `Dism`。
没有 `DismPersistence`、没有 `DismPersistenceProvider`、
没有 SQLDelight。绑定细节是 `private class`，关在各自文件里。

验收标准：**两个平台的入口调用处都不需要
`@OptIn(DismInternalApi::class)`**。

**2. 强制 `LOCAL`，而不是校验**

传 `IN_MEMORY` 进来时纠正配置，而不是报错或放行：

```text
调 JvmDismFactory.create 本身就是"我要落盘"的表达
若仅校验并放行内存模式 → 用户以为存下来了，重启后什么都没有
```

"看起来在落盘但其实是内存"比直接报错恶劣得多。

**3. 两个平台收不同的东西，这是刻意的**

```text
JvmDismFactory      收 File            桌面：应用自己决定路径
AndroidDismFactory  收 Context + 库名  Android：系统管路径，应用只给名字
```

Android 不允许应用随意选数据库位置。把 `Context` 塞进公共配置
会立刻破坏 KMP，所以入口必须住在 `androidMain`。

## 顺带修掉的一个 bug

`AndroidDatabaseDriverFactory` 把库名**硬编码**成 `"dism.db"`：

```kotlin
DismConfiguration(storage = DismStorageConfiguration(databaseName = "work"))
```

在 Android 上会**静默**落到 `dism.db`——用户以为数据分开存，
其实全在一个库里。桌面端没这个问题（路径决定名字），
两边语义不一致正是 bug 的来源。

现在库名是构造参数，默认值保持 `"dism.db"`，既有调用方不受影响。

## 验证

### 单元级（`JvmDismFactoryTest`，5 个）

```text
decisionSurvivesACloseAndReopen        实例 A 写 → 实例 B 从同一文件读出
separateFilesDoNotShareState           反证：两个文件互不串
localModeIsForcedRegardlessOf...       传 IN_MEMORY 仍必须落盘
parentDirectoriesAreCreated            ~/.dism/ 不存在时自动创建
defaultConfigurationIsNotLocal         不改变 DismFactory 的默认值
```

第二条是必要的：**"能读出来"本身不能证明数据被写到了这个文件里**。

### 端到端（真实启动桌面应用）

```text

```

## 覆盖情况（诚实版）

```text
桌面落盘    ✅ 单元测试 + 真实运行验证
Android     ⚠ 仅编译验证（无设备 / 模拟器可用）
```

Android 的「应用私有目录真的可写」「卸载重装后行为」这几件事
**没有在本机验证过**。

## 一个已知的门禁缺口：Android 不在 ABI 校验范围内

**`androidMain` 的公共 API 不在 ABI 校验范围内。**
详见 `docs/developer/compatibility.md` 的「目标覆盖」一节。

```text
实际生成的 dump
  jvm/core.api       JVM 主源集
  core.klib.api      iosArm64 / iosSimulatorArm64 / js / wasmJs

Android 两者都不含。
```

所以 `AndroidDismFactory` 是新增的公共 API，
而 `checkKotlinAbi` 通过了——不是因为它没问题，
而是因为它**没在看 Android**。

**已查证：这一项无法用 KGP 内置工具补上。**

```text
AbiValidationMultiplatformVariantSpec 只有一个 klib kind，
没有 jvm / android kind
variants 容器 DSL 已被移除
  （"Variants DSL was removed and is no longer supported"）
```

注意不要与 `keepLocallyUnsupportedTargets` 混淆：那个开关管的是
**本机编译不了的目标**（如 Windows 上的 iOS），KGP 会**推断**它们的
ABI 变化；Android 的问题是根本不参与校验模型。

**当前选择**：接受现状，并让 `androidMain` 的公共面保持极小
（目前只有 1 个类型，其实现是 1 行委托到与 `JvmDismFactory`
共享的、已有测试覆盖的 `DismBootstrapper` 路径）。
